# Day 08 Lab Report - LangGraph Agentic Orchestration

## 1. Architecture Explanation

The LangGraph support agent is built as a typed `StateGraph` backed by `AgentState` — a `TypedDict` that uses append-only `Annotated[list, add]` reducers for `messages`, `tool_results`, `errors`, and `events`, ensuring a complete, immutable audit trail for every run.

### Graph Topology

```
START → intake → classify → [conditional routing]
  simple       → answer → finalize → END
  tool         → tool → evaluate → answer → finalize → END
  missing_info → clarify → finalize → END
  risky        → risky_action → approval → tool → evaluate → answer → finalize → END
  error        → retry → tool → evaluate → [loop or answer]
  max retry    → dead_letter → finalize → END
```

### Key Design Decisions

- **LLM-based classification**: `classify_node` uses Gemini (`gemini-3.1-flash-lite-preview`) with `with_structured_output()` for semantic, priority-aware routing (Risky > Tool > Missing Info > Error > Simple). This avoids brittle keyword matching.
- **LLM-generated responses**: `ask_clarification_node` and `answer_node` use Gemini to produce natural, contextually grounded replies instead of hardcoded strings.
- **LLM Robustness**: All LLM calls are wrapped in `llm_invoke_with_retry()` with 3 retry attempts, 30-second timeout, and exponential backoff (2^n seconds). This handles transient API errors gracefully.
- **Deterministic evaluate**: `evaluate_node` uses a simple `"ERROR" in result` string check — appropriate because `tool_node` outputs predictable mock strings. Should be upgraded to LLM-as-judge when replaced with real API calls.
- **HITL approval**: When `LANGGRAPH_INTERRUPT=true`, `approval_node` calls `interrupt()` to freeze the graph and wait for human input. The Streamlit UI (`frontend/app.py`) resumes execution via `Command(resume=...)`.
- **PostgreSQL checkpointing**: `persistence.py` uses `PostgresSaver` backed by a Dockerized `postgres:16-alpine` instance with `autocommit=True` (required to allow `CREATE INDEX CONCURRENTLY` during `setup()`). Every run gets a unique `thread_id` ensuring isolated state history and crash-resume capability.

## 3. Failure Analysis

**S05_error / S11_retry_crash — Transient Tool Failure:**
The `tool_node` simulates failure for `route=error` on the first 2 attempts. The `evaluate_node` detects `"ERROR"` in the result and returns `needs_retry`. The `route_after_evaluate` edge loops back to `retry_node`, which increments `attempt` and returns to `tool_node`. On attempt 3, the tool succeeds. This demonstrates a bounded, self-healing retry loop.

**S07_dead_letter — Hard Failure (max_attempts=1):**
With `max_attempts=1`, `retry_or_fallback_node` increments `attempt` to 1 immediately. `route_after_retry` checks `attempt >= max_attempts` and routes directly to `dead_letter_node` — without ever calling `tool_node`. The DLQ node logs a structured entry for manual review and proceeds to `finalize`. No infinite loops are possible.

**S04/S06/S08/S09 — HITL Approval:**
All 4 risky scenarios correctly trigger `risky_action_node → approval_node`. In test mode (`LANGGRAPH_INTERRUPT=false`), `approval_node` returns mock `approved=True` and execution continues to `tool`. In UI mode (`LANGGRAPH_INTERRUPT=true`), the graph freezes at `interrupt()`, the Streamlit UI shows Approve/Reject buttons, and execution resumes via `Command(resume={...})`.

## 4. Bonus Extensions

### Real HITL with LangGraph `interrupt()`
Implemented via `LANGGRAPH_INTERRUPT=true` environment variable. When set, `approval_node` calls the native `interrupt()` API, which serializes state to PostgreSQL and suspends the graph process. The Streamlit frontend polls `graph.get_state()` to detect the interrupted task, displays the proposed action with risk metadata, and resumes via `graph.stream(Command(resume=...))`.

### Streamlit UI (`frontend/app.py`)
Full chat interface connected to the Postgres checkpointer. Supports multi-turn conversations per `thread_id`, live HITL approval cards, and automatic state recovery from DB on page reload.

## 5. Improvement Ideas

1. **Parallel Fan-out**: Use `Send()` to run multiple tool lookups concurrently (order status + customer profile), merging results via append-only reducers.
2. **Adaptive Retry Budget**: Adjust `max_attempts` based on error type — `503 Service Unavailable` retries 5 times; `401 Unauthorized` retries 0 times.
3. **Real Tool Integration**: Replace mock `tool_node` with actual API clients. Update `evaluate_node` to use LLM-as-judge for semantic result validation.
4. **Observability**: Stream `events[]` from `AgentState` to a time-series DB (InfluxDB) or APM tool for real-time latency and retry dashboards.
